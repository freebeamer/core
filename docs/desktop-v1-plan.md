# FreeBeamer Desktop V1 implementation plan

Date: 2026-09-01
Status: Completed

This plan records the delivered Desktop V1 milestone. Follow-on toolbar and
multi-cell editing work is tracked in
[`toolbar-and-table-tools-plan.md`](toolbar-and-table-tools-plan.md).

## Goal

Build a cross-platform desktop calibration editor on the validated FreeBeamer V0
engine. The application will use Wails and Go for the native shell and backend,
with Angular and TypeScript for the complete frontend.

Desktop V1 must let a user safely:

1. Open an XDF and BIN pair.
2. Review compatibility, identity, and checksum status before editing.
3. Search and browse maps in a conventional tuner-style left sidebar.
4. Inspect scalar, one-dimensional, and two-dimensional calibration data using
   the presentation appropriate to its shape.
5. Edit supported values with validation, undo, redo, and a byte-level change
   preview.
6. Save to a new BIN only after the existing Go checksum and post-verification
   safety gates pass.

ECU flashing, live data, cloud accounts, and general MEVD17 checksum support
remain outside this milestone.

## Fixed technology choices

- Native application: Wails v2 and Go.
- Frontend: Angular with TypeScript, generated by the Angular CLI.
- Angular structure: standalone components with lazy feature boundaries.
- UI state: Angular signals for synchronous workspace state; RxJS only for
  genuinely asynchronous streams and cancellation.
- Styling: custom SCSS and CSS design tokens using Angular CDK behavior
  primitives. Do not adopt a stock component theme as the product identity.
- Visualization: Plotly.js behind a small Angular adapter. Use heatmap and line
  traces for 2D views and WebGL surface traces for eligible 3D views.
- Backend boundary: generated Wails TypeScript bindings over explicit Go DTOs.
  The frontend must not parse XDF files, modify BIN bytes, or calculate
  checksums.
- Frontend tests: Angular's standard Vitest setup, plus browser-level tests for
  rendering and keyboard interaction.
- Go tests: existing package tests, fuzz targets, and desktop service tests.

Wails does not ship an Angular template, so the Angular application will live in
`frontend/` and `wails.json` will use `ng build` and `ng serve` as documented by
Wails. Production assets will be embedded into the desktop executable.

References:

- [Wails Angular integration](https://wails.io/docs/guides/angular/)
- [Wails Go bindings and embedded assets](https://wails.io/docs/howdoesitwork/)
- [Angular signals](https://angular.dev/guide/signals)

## Architecture

Keep the proven packages independent of Wails:

```text
Angular UI
    |
    | generated typed Wails bindings
    v
internal/desktop Service
    |
    +-- workspace session and DTO mapping
    +-- native open/save dialogs
    +-- undo/redo transaction history
    |
    v
pkg/xdf + pkg/binfile + pkg/calibration + pkg/identify + pkg/checksum
```

The desktop service owns one active workspace. A workspace contains the loaded
definition, immutable original image, mutable working image, edit history, and
checksum provider result. Angular receives presentation DTOs, never Go domain
objects with internal implementation details.

Long operations must accept cancellation or ignore stale responses using a
workspace generation ID. Opening another file pair must not allow an older
decode request to overwrite the new workspace state.

## Application layout

Use the familiar calibration-editor layout while keeping the hierarchy quiet
and corporate:

```text
+--------------------------------------------------------------------------+
| App menu | Open BIN | Open XDF | Save As | Undo | Redo | ROM status      |
+----------------------+---------------------------------------------------+
| Search maps          | Map title                              2D | 3D    |
| Categories/filter    | Units, address, dimensions, formula metadata      |
|                      +---------------------------------------------------+
| > Category           |                                                   |
|   Map name           |       active table / panel / visualization        |
|   Map name           |                                                   |
| > Category           |                                                   |
|                      +---------------------------------------------------+
|                      | selection details | raw value | decoded | address |
+----------------------+---------------------------------------------------+
| Changed cells | checksum state | compatibility | warnings                |
+--------------------------------------------------------------------------+
```

The left pane is resizable and contains search, category filters, favorites,
and the virtualized map tree. The center is a tabbed document workspace so a
user can keep multiple maps open. The bottom status area exposes unsaved edit
count and checksum state at all times.

Keyboard support is required from the first editable grid: arrow navigation,
Enter/F2 to edit, Escape to cancel, Delete to restore the original cell, and
standard undo/redo shortcuts.

## Visual design direction

The default and initial V1 theme is dark. It should look like professional
engineering software rather than a gaming dashboard.

- Neutral charcoal surfaces with three clear elevation levels.
- Cool blue as the primary action and selection color.
- Green, amber, and red reserved for verified, warning, and unsafe states.
- Compact density, restrained 4-6 px radii, thin separators, and no glow.
- Tabular numerals for addresses, raw values, decoded values, and checksums.
- A modern sans-serif UI font with a monospace companion for binary data.
- Minimum AA text contrast and visible keyboard focus on every control.
- Color is never the only indication of checksum or validation state.

Create tokens for surfaces, borders, text levels, status colors, spacing,
radius, typography, row height, and chart colors. Components consume tokens;
they must not contain scattered literal theme colors.

## Presentation policy by calibration shape

Every supported calibration remains editable in a grid or value panel. Charts
are coordinated views, not alternate sources of truth.

| Data shape | Default presentation | Optional presentation |
| --- | --- | --- |
| Scalar or flag | Labeled value panel with raw/decoded metadata | None |
| One varying axis | Compact editable row/column grid | 2D line chart |
| Two axes and a Z matrix | Editable matrix with frozen X/Y headers | Heatmap and 3D surface |
| Virtual or unaddressed axis | Metadata panel with explicit unsupported state | None |
| Invalid/unsupported map | Read-only diagnostics panel | None |

The 3D toggle is shown only when both axes vary and Z is a rectangular numeric
matrix. The surface uses decoded X, Y, and Z values, preserves the XDF row
orientation, shows units on every axis, and highlights the cell selected in the
grid. Camera changes must not modify data.

Large or degenerate matrices may disable 3D with a stated reason. Establish the
exact interactive cell threshold through profiling rather than silently
downsampling calibration data. If a preview is ever downsampled, label it as a
preview and keep editing attached to the full-resolution grid.

## Go desktop API

Start with a narrow service surface. Names may change during implementation,
but responsibilities should not:

```text
OpenWorkspace(xdfPath, binPath) -> WorkspaceSummary
ChooseAndOpenWorkspace() -> WorkspaceSummary
GetWorkspace() -> WorkspaceSummary
ListMaps(filter) -> MapPage
GetMap(mapID) -> MapDetail
SetCell(mapID, row, column, value) -> EditOutcome
SetIndex(mapID, index, value) -> EditOutcome
Undo() -> EditOutcome
Redo() -> EditOutcome
GetDiff() -> DiffSummary
VerifyChecksums() -> ChecksumSummary
SaveAs(path) -> SaveOutcome
ChooseAndSaveAs() -> SaveOutcome
CloseWorkspace(force) -> void
```

Map IDs must be stable within a workspace and must not rely on titles being
unique. DTOs include units, formulas, dimensions, raw and decoded values,
physical addresses, edit state, and visualization eligibility.

`SaveAs` must operate transactionally: clone the working image, correct only
through the registered checksum provider, post-verify every region, write a new
file, and report the final hash. It must never overwrite the original BIN in V1.

## Angular frontend structure

Organize by product feature rather than technical artifact type:

```text
frontend/src/app/
  core/             Wails gateway, errors, dialogs, keyboard commands
  workspace/        workspace store and document tabs
  map-browser/      search, categories, favorites, virtualized tree
  map-editor/       scalar panel, axis grid, matrix editor, cell inspector
  visualization/    line, heatmap, surface, Plotly adapter
  changes/          diff list, undo/redo history, save review
  shell/            toolbar, split panes, status bar, theme
  shared/           focused reusable controls and formatting pipes
```

Use one workspace store backed by signals. Components receive readonly signals
and call store commands; they do not invoke generated Wails functions directly.
The Wails gateway is the only frontend layer aware of generated binding paths.

## Delivery phases

### Phase 0 - Toolchain and shell

- Pin Wails, Angular, Node, and package-manager versions.
- Add `frontend/`, Wails application entry point, embedded assets, and
  `wails.json` Angular commands.
- Add repeatable `desktop:dev`, `desktop:test`, and `desktop:build` commands.
- Prove a production desktop build can call a typed Go health method.
- Keep the existing CLI operational from the same Go module.

Acceptance: Go tests pass, Angular tests pass, and a Wails production build
opens a dark empty shell on the primary development platform.

### Phase 1 - Workspace and inspect screen

- Add native XDF/BIN file selection and recent-file metadata.
- Build the Go workspace service around existing V0 packages.
- Display ROM hash, ECU identity, XDF counts, compatibility, and checksums.
- Refuse an editing session when the current V0 engine would reject it.
- Add clear empty, loading, error, and unsupported states.

Acceptance: opening the private V0 fixture reproduces the CLI `inspect` result
without duplicating identification or checksum logic.

### Phase 2 - Map browser and read-only editors

- Add virtualized search and category navigation for all 962 fixture maps.
- Add document tabs and selection persistence.
- Implement scalar, 1D, and matrix read-only presentations.
- Show raw value, decoded value, units, formula, and address for a selected cell.
- Profile initial list load, search, and representative large-map rendering.

Acceptance: every addressed fixture map opens without UI lockup and matches the
existing Go decoder output.

### Phase 3 - Visualization

- Add line plots for one-axis tables.
- Add heatmaps for two-axis matrices.
- Add interactive 3D surfaces only for eligible two-axis matrices.
- Synchronize hover/selection between chart and grid.
- Handle resize, tab suspension, dark-theme chart tokens, and WebGL failure.

Acceptance: representative scalar, 1D, 6x6, and larger matrix fixtures choose
the correct presentation; 3D values and orientation match the grid exactly.

### Phase 4 - Editing and history

- Add validated cell and index editing through the Go calibration service.
- Show requested, encoded, raw, and round-tripped values before commit.
- Add dirty markers, changed-cell styling, undo, redo, and restore-original.
- Keep grid, cell inspector, heatmap, and surface synchronized after edits.
- Add a full byte diff view grouped by calibration edit.

Acceptance: the Performance gauge test edit changes exactly the expected byte,
undo restores the original hash, and redo restores the same modified hash.

### Phase 5 - Safe save workflow

- Add a save-review screen with destination, changes, provider, and warnings.
- Verify before correction, correct a clone, post-verify, then save as a new BIN.
- Refuse unsupported firmware, unsafe checksum damage, and original-path writes.
- Display saved SHA-256 and provide a way to inspect the saved artifact.
- Handle cancellation, disk errors, and partial-write cleanup safely.

Acceptance: the complete V0 mutation/correction oracle passes through the UI,
the saved file verifies all 11 regions, and the original fixture is unchanged.

### Phase 6 - Product hardening and packaging

- Add native menus, keyboard shortcut reference, crash/error logging, and an
  About panel containing exact versions.
- Test Windows, macOS, and Linux windowing and WebView behavior.
- Produce signed/notarized installers only after platform-specific release
  procedures are documented.
- Add accessibility, high-DPI, minimum-window-size, and performance passes.
- Preserve the existing experimental/no-flashing safety language.

Acceptance: reproducible production builds pass the release checklist on every
supported target platform.

## Test strategy

### Go

- Unit-test the desktop service with temporary fixtures and fake dialog ports.
- Assert DTO mapping against the existing private fixture tests.
- Test workspace generation IDs, cancellation, undo/redo, dirty state, and
  transactional Save As behavior.
- Continue running `go test ./...`, `go vet ./...`, and the existing fuzzers.

### Angular

- Unit-test stores, formatters, eligibility rules, and Wails gateway adapters.
- Component-test keyboard editing, validation, filters, tabs, and status states.
- Use deterministic chart-adapter tests rather than snapshotting Plotly markup.
- Browser-test grid/chart synchronization, resizing, focus, and WebGL fallback.
- Keep one end-to-end acceptance path for open, edit, undo, redo, verify, and
  Save As using a non-proprietary deterministic fixture.

### Visual quality

- Maintain reference screenshots for the empty workspace, inspect screen,
  scalar panel, 1D table, matrix heatmap, 3D surface, diff review, and checksum
  error state at standard and high-DPI sizes.
- Review contrast, truncation, focus order, dense numeric alignment, and status
  clarity instead of relying only on pixel diffs.

## Definition of Desktop V1 complete

Desktop V1 is complete when a user can open the validated fixture, see the same
compatibility result as the CLI, find and inspect all supported maps, edit the
Performance gauge map in the matrix or synchronized 3D view, review and undo the
exact byte change, redo it, save a checksum-corrected copy, and verify that copy
without any mutation of the original BIN.

The first implementation task is Phase 0 only: scaffold Wails around the
existing module, create the Angular TypeScript frontend, establish the dark
design-token shell, and prove one typed health call across the boundary.
